User flow — what comes after what

Every screen, in the order a parent meets them, with the state each one reads and writes and the dead ends each one can reach.

Built from the code, not from the PRD: routes under app/, questions from app/intake/questions.ts, storage from lib/ui/profile-store.ts, the answer pipeline from app/api/ask/route.ts. Colours are the design-system.md §2 tokens.

1The spine

The path almost every parent takes, once. Four screens, no account, nothing stored on a server.

/
The promise: “Every deadline. Both countries. In English. Sourced.”
Reads nothing · Writes nothing · static
parent starts the intake
/intake
Seven questions, one per screen, then a review of all seven before anything is saved.
Order: due date → state → city → passports → employment → marriage → first child → review
Writes babysteps.profile.v1 to localStorage, under an anonymous id
Reads nothing — arriving here with a profile already stored does not prefill it
One clock read for the whole flow, so validation cannot shift under a parent who leaves the tab open across midnight
on the review step, saves and routes
/timeline
The hero screen. Date gutter, hairline rail, the today band, “Do next”.
Reads the profile from localStorage · POST /api/timeline
Dots are filled for confirmed dates, hollow for estimated. Consular items carry a 3px violet border.
taps any deadline
/item/[id]
One deadline in full: what it is, when, what to take, who decides, the source.
Three controls: mark done · add to calendar · back to the timeline
Statically prerendered; the dates are filled in by a client island from the reader’s own profile

The one thing that surprises people

The profile lives in localStorage on one browser. There is no account, so nothing follows the parent to another device. Opening /item/… on a fresh phone shows the page but no “Add to calendar” button at all — the control returns nothing when there is no profile, rather than rendering disabled. The intake has to be done on the device you are testing.

2The four branches

Everything else hangs off the timeline or an item page. None of it is on the spine.

From /timeline
/birth the proof
The parent types the real birth date and the estimated deadlines move, in front of them.
POST /api/birth-preview computes the diff — the client never calculates a date
Nothing commits until the button is pressed; the commit is a localStorage write
Six dates move at once, which is why the diff is shown before it is committed. 400ms, and nothing else on the screen moves.
/share/[token] read-only
A link for the partner. Minted on request, never on page load.
POST /api/share returns a signed token; the URL is assembled in the browser from the current origin
Rendered entirely on the server, so the partner needs no profile and nothing about them is stored
Read-only means read-only: no share control, no birth prompt, no links into item pages
From /item/[id]
POST /api/ics file download
This one deadline as a calendar file — one event, one alarm, ~1.7 KB.
Never touches the database; every date comes from the rules on disk
Marked TRANSP:TRANSPARENT, so a deadline does not block the parent’s availability
Carries no METHOD, ORGANIZER or ATTENDEE — it is an entry to import, not an invitation (ADR-085)
From anywhere
/ask guarded
A question, answered only from cited official sources.
POST /api/ask → validate → rate limit → medical guard → expand → retrieve → generate
The wait is an honest skeleton, not streaming: nothing renders without a validated citation
An “answered” reply carrying no citation draws nothing — an uncited answer is a failure, not a degraded success

4Where the flow stops

Every one of these is a designed state, not an error page. They are the most useful things to test, because they are the ones nobody sees by accident.

ConditionWhat the parent seesSeverity
No profile in this browser /timeline routes to the intake. On an item page the calendar button is absent entirely. by design
localStorage unavailable or blocked The intake checks before it starts and reports a save failure rather than losing seven answers silently. guard
A stale or hand-edited storage key Treated as “no profile yet” and discarded, never migrated in place. It must look identical to a first visit. by design
The item is not on this profile’s timeline /api/ics answers 404 not_on_your_timeline — a request for an event that does not exist for this family, not a server error. by design
A clinical question Deflected by the medical guard before expansion, embedding, retrieval or any provider sees it. guard
Retrieval below the confidence floor A refusal naming the authority who does answer — never a guess. guard
21st question in a day 429: “That is as many questions as we can answer for you today. The limit resets after a day.” guard
An invalid or tampered share token 404. The signature is checked before a timeline is built. security
The database is paused or unreachable The timeline, the item pages and the calendar export keep working — none of them touch the database. Only /ask degrades. by design

Why so much of this is client-side

No account was a product decision, so the profile has nowhere to live but the browser. That one choice explains the shape of everything above: why the timeline is a client screen, why item pages are prerendered shells filled in by an island, why the partner’s view had to be rendered on the server from a signed token instead of a shared login, and why there is a device boundary that a parent can walk across without warning.

6Walking it on a device

The order to test in, so that each step leaves the state the next one needs.

  1. Open / on the device itself. Not a link from elsewhere — the point is a cold start on a cold network.
  2. Complete the intake. All seven questions, thumb only. This is what creates the profile; nothing below works without it.
  3. Read the timeline. Check the gutter alignment, that the today band is the only full-bleed element, and that consular items are visibly a second track.
  4. Open a deadline — standesamt_birth_registration is a hard statutory one, so nothing about it is estimated.
  5. Export the calendar file and import it. Import on a computer, or open it from Mail on iPhone. Check: one alarm not two, the entry shows as Free, and the link opens the item page.
  6. Open an estimated deadline — elterngeld_application or kindergeld_application — and confirm it says so, both on screen and inside the calendar entry.
  7. Record a birth date at /birth and watch six dates move at once. Then check the item pages agree with the timeline.
  8. Ask one question and time it to the first text.
  9. Make a share link and open it in a private window, where there is no profile — it must still render in full.
  10. Switch the device to dark mode and walk back through. No real device has confirmed it.
